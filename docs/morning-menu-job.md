# Morning menu — the job's instructions (escrow copy)

The saved instructions of the `morning-menu` cron job (daily 05:20 America/Phoenix, owner goal:morning-agenda-briefing), copied 2026-10-31 so the production copy stands alone outside Muse.

---

Build the morning menu — the ONE place last night's reporting reaches the admin (the admin's orders, 2026-10-31, the Morning Menu restructure, final form after the one-shot chat buttons failed him). The admin ended the per-job chat text dumps and the one-shot option buttons: overnight results reach him as a WEB PAGE on his menu site — https://claypnw.github.io/menu/morning.html — rebuilt every morning by this job, that he can open any time and tap in any order, as often as he likes. The page is an index only: one row per item with its status, each row's link opening that item's OWN separate report. There is no combined morning report, in any form, ever, and no chat options buttons for menu items, ever.

Run at 05:20 Arizona time, after the night's jobs and the 5:00 AM morning check have finished. "Today" is today in America/Phoenix; "yesterday" is the day before it.

FORM (the hourly status report's form, and ITIL morning-report practice — the admin named both as the model): every item carries its status for the night — finished / finished with an exception named / had an error / no record — in plain words, and every count or fact rests on a named record read this run (a verify log, a finish line, the report file itself). An exception is never hidden inside a clean status. A missing file is "no record", never "finished". Each item carries TWO status wordings: "status" — the full line, for this record and the finish line; and "page_status" — the short plain line printed on the page (a few words, the same facts, nothing new).

STEP 1 — COLLECT THE NIGHT'S REPORT FILES. Check each exists (a file check, this run — never from memory). Only items that exist go on the menu, in this fixed order. For each item, set its "slug" (the name its report copy carries on the menu site) and its "links" (the row's links, each with its full link text and its href — an http(s) URL is used as it stands; a local file path is copied by the builder under morning-files/<today>-<slug><ext>):
1. The Payson Morning Scroll — slug null. Link: text "1 · The Payson Morning Scroll", href the edition's live PDF on the Scroll site: https://claypnw.github.io/morning-scroll/payson-morning-scroll-<today>.pdf. Status from the Scroll chain's dated verify log (~/workspace/morning-post/batch/logs/, the newest verify-<today>-*.log) and the briefing job's line in the completion pile.
2. Last night's KPIs — slug "kpi". Link: text "2 · Last night's KPIs", href the local file ~/workspace/your_files/kpi-page-<today>.pdf. Status from the morning check's night record (~/workspace/goals/morning-agenda-briefing/hidden_files/morning-kpi-records/night-<today>.json): the finished count out of the set total, the failed count, the no-record count.

Status from its dated verify log (~/workspace/batch-logs/github-billing-watch/<today>.log): the cycle minutes and their percentage. STEP 2 — COLLECT PENDING DECISIONS. Read the completion pile in ~/workspace/OPEN-WORK.md: every line in the "Finished — awaiting morning report" section not yet marked REPORTED, plus any line from last night's jobs that names an open proposal or a choice waiting on the admin (for example the community check's 15-day source proposal, or a maker-finds question). Write each pending decision in plain words, with its choices stated (the words the admin would tap), one decision per entry. A pile line that is a plain result with no choice in it is not a decision — it is covered by its item's status line in step 1 and is not repeated here.

STEP 3 — WRITE THE MENU RECORD. Write ~/workspace/goals/morning-agenda-briefing/hidden_files/morning-menu-<today>.json: {"date": <today>, "items": [ {"n": 1, "name": <the option's name>, "slug": <the copy slug or null>, "page_status": <the short line for the page>, "status": <the full status words>, "record": <the named record the status rests on>, "links": [ {"text": <the link's full text>, "href": <the URL or local file path>} ... ]} ... ], "decisions": [ {"question": <plain words>, "choices": [<choice>, ...], "record": <where the decision stands>} ... ]}. The record is the proof the finish line rests on; counts in it come from the records read in steps 1–2, never from memory.

STEP 4 — BUILD AND PUBLISH THE PAGE. Run the fixed builder program:
python3 ~/workspace/morning-post/batch/build_morning_menu.py --date <today>
It reads the menu record, renders the page (title "Morning Menu — <weekday, date>"; one row per item — its links and its page_status line; the pending decisions as plain text lines with their choices named; the closing lines: the page is rebuilt every morning, and anyone holding the page's address can open it and the reports behind it), and publishes in one run of the GitHub key program to the menu repository (claypnw/menu): morning.html, the dated archive copy morning-<today>.html, and the report copies under morning-files/<today>-<slug><ext>. The step counts as done only when the builder ends VERDICT: PASS. If it ends VERDICT: FAIL, the run ends abnormally (below) — never hand-write a page instead.

STEP 5 — HAND OFF. The run's result is ONE short handoff to the main chat, and the run sends no other chat text: one line saying the morning menu is ready, with the page address https://claypnw.github.io/menu/morning.html, the counts (menu items, pending decisions), and the pending-decisions list from step 2, each with its choices. The main agent sends the morning message from this handoff: the one line plus the page link, with each pending decision's choices as tappable buttons under the link. No menu-item buttons are ever made (they die after one tap — the admin's ruling, 2026-10-31). Do not paste report content or add summary prose — the handoff is the line, the link, and the decisions, and nothing else.

END STATE (the standard two states — a run ends in exactly one): on a clean end, write the finish line by running:
python3 ~/workspace/work-launcher/write_finish_line.py finish "Morning menu" "<today, YYYY-MM-DD>" "<menu items count> menu items, <decisions count> pending decisions, page published" "~/workspace/goals/morning-agenda-briefing/hidden_files/morning-menu-<today>.json"
On an abnormal end — a crash, a timeout, a stop mid-step, the builder's VERDICT: FAIL: (1) CAPTURE what failed and at which step, in the menu record file if it exists yet, else in the day's record under the same folder; (2) write the ERROR line with the shared writer (error mode) naming the failure and the cleanup; (3) CLEANUP: a partial menu record is removed, never left half-written — the dated record either stands whole or does not stand. One missing report file is NOT an abnormal end: the item is simply left off the menu and, where its job's record shows the report was owed, the item's absence is named in the handoff as a plain fact with its record.

Do not modify MEMORY.md.
